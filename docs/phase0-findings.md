Key facts:
- **The sandbox container is granted `NET_ADMIN` + `NET_RAW`** (`docker_client.py` header, delta 2).
  So any firewall *inside* the sandbox can be flushed by the agent and is **not** an enforcement point.
- The Strix agent loop runs **on the host** and drives the sandbox via docker. LLM traffic leaves from the host,
  not the sandbox, so the sandbox only needs target traffic.
- Correction to C10: White hat → whitebox **only if** a source-code path is supplied (new optional project field).
- Function tools can't be disabled by flag. Options: (a) remove keys/env (web_search, telemetry);
  (b) a penenv launcher that imports strix and filters `_BASE_TOOLS` before the first agent build (a supported pattern: `register_agent_tools` lives in the same module). Decide in T5.2.

## T0.5 Network enforcement — done (demo passed)
Re-runnable demo: `scripts/egress-experiment.sh` (image `docker/egress-gw`); recorded output:
`docs/t05-egress-demo.log`. Results, with the sandbox started exactly as Strix starts it
(NET_ADMIN + NET_RAW; note the `pentester` user also has **passwordless sudo**, so the agent is root
in its own netns):

| Probe from sandbox | Result |
|---|---|
| before the default route is set | no egress at all (fails closed) |
| allowlisted target `172.20.0.2:3000` | HTTP 200 |
| allowlisted host, other port (22) | blocked |
| decoy `172.20.0.3:80` via curl | blocked |
| decoy via `nmap -sS -Pn` (root) | all ports `filtered` |
| internet `1.1.1.1:443` | blocked |
| **host via the network bridge IP `:22`** | **reachable in the first run (SSH banner)** → fixed with `com.docker.network.bridge.inhibit_ipv4=true` (host gets no IP on the scan network); now refused |
| root tampering (new routes, neighbour flush) | still blocked (enforcement is in the gateway's netns) |
| external DNS | none (docker embedded DNS does not forward on internal networks) |
| decoy tcpdump | **0 packets** from the sandbox (link-local multicast noise excluded) |

Consequences for the design:
- Because the host has no IP on the scan network, Strix's host→sandbox Caido channel is carried by the
  gateway: a loopback-published port DNATs to the sandbox. The penenv launcher patches
  `_resolve_exposed_port` to install the sandbox route, `/etc/hosts` entries and that DNAT, and returns the
  published endpoint — so there is no start-up race.
- No DNS in the sandbox: in-scope hostnames are resolved on the host at plan time and written to
  `/etc/hosts`; everything else fails to resolve (another scope guard, and it closes DNS exfiltration).

Original design notes:
- No passwordless sudo → host `DOCKER-USER` rules are not available without your intervention.
- Rootless design: a per-scan `docker network create --internal penenv-scan-<id>` plus an
  **egress-gateway container** (its own netns, its own NET_ADMIN, attached to both the internal network and
  the outside). It forwards and NATs only the allowlisted in-scope IPs/CIDRs:ports and explicitly drops
  out-of-scope ones. The sandbox joins only the internal network (`STRIX_DOCKER_SANDBOX_NETWORK`), so the
  gateway is its only route out. The agent's NET_ADMIN only affects its own netns.
- Open questions the experiment must answer: (1) can the host-side Strix still reach the sandbox's tool
  server/Caido on an internal network? (2) how the sandbox's default route is pointed at the gateway
  (post-create `docker exec ip route`, which races with Strix startup, vs. a gateway at the network's gateway IP).
  If (1) fails, fallback is a one-time root setup of `DOCKER-USER` rules scoped to penenv networks (you run one `sudo` command).

## T0.6 KeePassXC authenticator — done
- `keepassxc-cli 2.7.12`. There is no CLI verb to set a TOTP seed. **Register** = build an entry XML with an
  `otp` attribute (`otpauth://totp/...`) → `keepassxc-cli import` into a temp kdbx → `merge -s` into the
  authenticator DB. **Recover** = `keepassxc-cli show -q -t db entry`.
- Verified: KeePassXC's code for RFC 6238 seed `12345678901234567890` matched an independent Python RFC 6238
  computation (783363 at the test instant).
- Password via stdin works and is absent from `/proc/<pid>/cmdline`.
- Caveat → mitigation: the temporary import XML holds the seed, so write it into a 0700 dir under
  `$XDG_RUNTIME_DIR` (RAM-backed tmpfs) and unlink it immediately after the merge.
